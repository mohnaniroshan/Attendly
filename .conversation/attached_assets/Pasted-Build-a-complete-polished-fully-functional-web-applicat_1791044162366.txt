Build a complete, polished, fully functional web application from scratch called:

ATTENDLY
"Your semester, organized."

Attendly is a personal college attendance management and semester planning application.

IMPORTANT:
This must be a REAL working application, not a static UI mockup.

The app must have working:
- JSON timetable import
- automatic timetable generation
- automatic subject creation
- attendance tracking
- attendance customization
- attendance history
- timetable editing
- daily attendance logging
- attendance calculations
- future attendance simulation
- trip/absence planning
- browser persistence

Do not create fake buttons or placeholder functionality.

Do not hardcode my current semester or timetable into the application.

The JSON provided later is SAMPLE IMPORT DATA only. The application must work with completely different semester JSON files.

==================================================
1. CORE CONCEPT
==================================================

Attendly is built around three separate concepts:

1. TIMETABLE
What classes are scheduled to happen.

2. REAL ATTENDANCE
What actually happened in those classes.

3. SIMULATION / PLANNER
What would happen under a hypothetical future scenario.

These must remain separate.

A planner simulation must NEVER modify real attendance, history, or timetable data.

The core workflow is:

JSON timetable
      ↓
Import + validation
      ↓
Automatic timetable generation
      ↓
Automatic subject/course creation
      ↓
User sets current attendance
      ↓
Daily attendance tracking
      ↓
Attendance history
      ↓
Future attendance / trip planning

6. SUBJECT / CLASS TYPE HANDLING
==================================================

The sample JSON uses names such as:

"SE & Testing PP"
"Machine Learning PP"
"Machine Learning PR"

In the current JSON convention:

PP = Theory
PR = Practical

The importer should detect this convention when present.

For example:

"Machine Learning PP"

should internally represent:

Base subject:
Machine Learning

Class type:
Theory

And:

"Machine Learning PR"

should represent:

Base subject:
Machine Learning

Class type:
Practical

IMPORTANT:

Theory and Practical must be treated as separate attendance records.

For example:

Machine Learning Theory
24 / 28

Machine Learning Practical
18 / 20

Do NOT combine these into a single 42/48 attendance figure unless the user explicitly chooses to view a combined subject summary.

The application must NOT permanently depend on PP/PR naming.

If future JSON does not use PP/PR, the importer should still work and allow the class type to be selected or edited.

==================================================
7. AUTOMATIC SUBJECT CREATION
==================================================

After successful import, automatically create the necessary subject/class records.

The user must NOT manually recreate every subject.

Do not assume the user's current attendance is zero.

Imported records may initially display:

0 / 0

The user must then be able to customize their current real attendance.

Example:

Operating Systems
0 / 0

User changes it to:

27 / 32

Attendly should then treat:

27 = attended
32 = delivered

as the current real attendance.

This allows the user to start using Attendly in the middle of a semester.

8. ATTENDANCE CUSTOMIZATION
==================================================

Every attendance record must allow editing of:

Attended
Delivered

Validation:

- attended >= 0
- delivered >= 0
- attended <= delivered
- integers only

Always display both fraction and percentage.

Example:

27 / 32
84.38%

Never show only the percentage.

Attendance editing must update all relevant calculations immediately.

==================================================
9. ATTENDANCE THRESHOLD
==================================================

Default threshold:

75%

Make the threshold configurable in Settings.

Do not hardcode 75% inside calculation functions.

Changing the threshold must automatically update:
- attendance status
- safe-bunk calculations
- recovery calculations
- planner projections

==================================================
10. ATTENDANCE CALCULATIONS
==================================================

Attendance percentage:

attended / delivered × 100

Overall attendance MUST be calculated using aggregate totals:

total attended
--------------
total delivered

Do NOT calculate overall attendance by averaging subject percentages.

Implement accurate calculations for:

- attendance percentage
- safe bunks
- recovery classes
- projected attendance
- threshold checks

Handle:
- 0 / 0
- 0 delivered
- exactly at threshold
- above threshold
- below threshold
- 100% attendance

Avoid divide-by-zero errors.

19. FUTURE CLASS OCCURRENCES
==================================================

The planner must calculate actual future class occurrences from:

- timetable day
- selected date range
- class time
- subject/class record

For example, if the timetable says:

Monday
Operating Systems
09:00–10:00

and the selected date range contains three Mondays, the planner must identify three separate class occurrences.

Do NOT simply multiply weekly class counts without considering actual calendar dates.

This is essential for trips spanning weeks and month boundaries.

==================================================

Planner calculations must NEVER modify:

- actual attendance
- attendance history
- timetable
- subject records

All planner results are hypothetical.

Clearly label them as:

Projected
Simulation
What If

Only real attendance actions may modify actual attendance.

23. RECOVERY CALCULATION
==================================================

Recovery calculations must start from the projected POST-TRIP attendance.

Example:

Current:
30 / 40 = 75%

After trip:
30 / 44 = 68.18%

Recovery must start from:

30 / 44

NOT:

30 / 40

Calculate the number of future attended classes required to reach the configured threshold.

Show:

"Attend X future classes to reach 75%"

24. ATTEND EVERYTHING COMPARISON
==================================================

Allow the planner to compare:

If I attend all scheduled future classes

versus

If I take the planned absence/trip

Show the projected difference without modifying real attendance.
